# 可行性研究报告

> **版本状态**：v0.8 规划版，基于根目录 `项目.md` 编制，尚未与实际代码和测试结果核对，详见 `00-文档说明.md`。

## 1. 引言

### 1.1 编写目的

本报告从问题定义、技术可行性、经济可行性、操作可行性和风险控制等方面，分析“艺术培训机构全流程教务管理平台的设计与实现”项目是否适合作为本科毕业设计实施，并为后续需求分析、概要设计和详细设计提供依据。

### 1.2 项目背景

艺术、兴趣类培训机构在日常运营中通常需要同时处理招生报名、班级管理、教师排班、教室预约、课堂考勤、课时扣减、学员作业点评、收费退费、教师薪资和经营统计等事务。若依赖 Excel、纸质表格或多个分散工具，容易出现排课冲突、课时误扣、学员信息分散、财务统计滞后和薪资核算不准确等问题。

本项目拟通过 Spring Boot + uni-app 移动端 + Vue3 管理后台前后端分离技术，实现一套覆盖家长端、教师端、教务端、财务端和超级管理员端的综合教务管理平台，提高机构教务与经营管理效率。

### 1.3 研究内容

- 教培机构教务数字化流程分析；
- 智能排课与冲突检测规则设计；
- 课堂考勤与课时自动扣减机制设计；
- 教师课时统计与薪资自动核算；
- 学员学情记录与成长档案管理；
- 招生、到课率、课时消耗、营收、教师工作量等运营数据统计分析。

## 2. 问题定义

当前培训机构常见问题包括：

| 问题 | 表现 | 系统改进方向 |
|---|---|---|
| 排课管理复杂 | 教师、教室、班级时间冲突难以及时发现 | 引入排课冲突检测与教室预约管理 |
| 课时统计不准确 | 人工扣课时易漏记或重复扣减 | 建立课时账户和课时流水 |
| 学情反馈分散 | 家长难以及时了解考勤、作业和教师评语 | 建立课堂作业、点评和成长档案 |
| 财务核算耗时 | 收费、退费、薪资依赖人工汇总 | 建立收费台账、退费审核和薪资结算规则 |
| 经营数据滞后 | 管理者难以及时看到招生、营收、到课率等指标 | 建立数据看板与报表导出 |

## 3. 可行性分析

### 3.1 技术可行性

系统计划采用成熟的前后端分离技术栈：

| 技术 | 用途 | 可行性说明 |
|---|---|---|
| Spring Boot | 后端 REST API、业务逻辑、事务控制 | 生态成熟，适合快速开发毕业设计系统 |
| MyBatis-Plus/MyBatis | 数据访问层 | 支持通用 CRUD 与复杂 SQL，适合教务统计查询 |
| MySQL 8.0 | 业务数据持久化 | 事务能力强，适合课时、财务、薪资等一致性场景 |
| Redis | 缓存、提醒、排课冲突辅助数据 | 可用于课表缓存、验证码、热点统计等扩展能力 |
| uni-app + Vue3 + Element Plus | uni-app 适合家长/教师移动端，Vue3 + Element Plus 适合教务/财务/管理员后台 | 终端分工清晰，符合真实使用场景 |
| ECharts | 数据可视化 | 满足营收、到课率、课时趋势等图表展示 |
| JWT | 登录鉴权 | 适合前后端分离架构下的无状态认证 |

智能排课可先采用“规则约束 + 时间交叉冲突检测 + 批量生成课次”的方式实现，课时扣减和薪资核算可通过事务与规则表实现，因此技术路径清晰可落地。

### 3.2 经济可行性

项目主要依赖开源软件和本地/云端基础环境，开发成本较低。对于培训机构而言，系统可减少人工排课、课时统计、薪资核算和财务对账成本，降低数据错误造成的管理损失，具备较好的应用价值。

### 3.3 操作可行性

系统按岗位划分功能：家长只关注报名、课表、学情和课时；教师只关注授课、考勤和点评；教务负责课程、班级和排课；财务负责收费、退费和薪资；超级管理员负责权限和全局看板。角色边界清晰，符合真实机构岗位分工，具备良好的可操作性。

### 3.4 法律与安全可行性

系统不接入真实支付通道，毕业设计阶段可采用模拟支付或线下收费登记方式。系统涉及学员、家长手机号和财务数据，应通过密码加密、角色权限控制、敏感操作日志和数据库备份等措施保证数据安全。

## 4. 方案比较

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| Excel/纸质台账 | 成本低、上手快 | 数据分散、易出错、难统计 | 不适合完整毕业设计系统 |
| 购买 SaaS 教务系统 | 功能成熟 | 不具备自主设计与论文实现价值 | 不作为本课题实现方式 |
| Spring Boot + uni-app + Vue3 管理后台自主开发 | 可完整覆盖软件工程过程，便于论文阐述 | 开发工作量较大 | 采用 |
| 微服务架构 | 扩展性强 | 毕设阶段复杂度过高 | 暂不采用，作为未来扩展 |

## 5. 风险分析与应对

| 风险 | 影响 | 应对措施 |
|---|---|---|
| 功能范围较大 | 开发周期紧张 | 优先实现报名、排课、考勤扣课时、收费、薪资和统计核心链路 |
| 排课规则复杂 | 智能排课难度上升 | 毕设阶段采用规则检测与人工调整结合，不追求工业级最优排课 |
| 课时与财务一致性要求高 | 数据错误影响演示可信度 | 课时账户、课时流水、收费记录使用事务控制 |
| 多角色权限易混乱 | 可能出现越权访问 | 统一 JWT 鉴权和角色菜单/API 权限控制 |
| 真实业务数据不足 | 统计图表无数据 | 使用初始化数据和模拟测试数据支撑演示与测试 |

## 6. 可行性结论

本项目技术路线成熟、业务场景明确、毕业设计成果形式完整，能够覆盖任务书要求的可运行系统、数据库脚本、设计文档、测试报告、论文和答辩材料。项目可行，建议按 `02-项目开发计划.md` 的阶段推进。
