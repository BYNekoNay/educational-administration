## A 类：技术选型

### Q1. 为什么用 Spring Boot 3，而不是更成熟的 2.7？

考察意图：确认选型是有依据的，不是因为「新」而新，也验证对 JDK 基线的理解。

回答要点：
- 本系统基线是 JDK 17。Spring Boot 3 是官方为 JDK 17 及以上设计的版本线，2.7 主要面向 JDK 8 到 11，用它反而要在兼容层上做妥协。
- 我们需要的几个能力，3.2.5 都给得很顺：内置容器方便打独立可运行 JAR、便于做容器镜像；Actuator 直接提供健康与就绪探针、指标暴露，是我们生产可观测性的底子；定时任务机制被流失预警的月度统计用到。
- 迁移成本对我们不构成问题，因为这是新项目，没有历史代码包袱。
- 一句话：选 3 不是追新，是让 JDK 17 基线和容器化部署都落在最省事的版本线上。

佐证材料：`docs/thesis/03-第2章-相关技术介绍.md` §2.3；`docs/thesis/04-第3章` §3.5。

### Q2. 为什么用 MyBatis-Plus，而不是 Spring Data JPA 或纯 MyBatis？

考察意图：考察对持久层框架取舍的理解，尤其是复杂统计场景。

回答要点：
- 系统的查询有一大块是复杂统计，比如营收、课程盈利、班级活跃度、教师工作量，这些用 JPA 的对象映射反而绕，用 MyBatis 手写 SQL 最直接。
- 但纯 MyBatis 又要写大量样板代码。MyBatis-Plus 正好两者兼顾：保留手写 SQL 的灵活性，同时提供通用 CRUD、分页插件、逻辑删除、乐观锁这些开箱能力。
- 对我们最关键的是它的乐观锁和逻辑删除：课时账户、退费审核、薪资流转这些「读-改-写」操作，统一走乐观锁，是并发纪律能落地的技术基础；用户等核心表用逻辑删除，删除变成标记。
- 一句话：统计要手写 SQL，工程要少样板、要并发控制，MyBatis-Plus 同时满足这两头。

佐证材料：`docs/thesis/03-第2章` §2.3；`docs/12-核心算法设计文档.md` §4.2。

### Q3. 为什么移动端用 uni-app，不直接做原生微信小程序？

考察意图：考察是否理解「一套代码多端」的实际收益和代价。

回答要点：
- 我们的移动端用户是家长和老师，使用场景是课表、报名、考勤、消息这类高频轻量操作，对多端覆盖有真实需求。
- uni-app 用 Vue 语法写一套代码，可以编译到 H5 和微信小程序。这和我们的管理后台是同一套 Vue 技术栈，团队学习成本低，家长在网页端和小程序端也都能用。
- 更重要的是一致性：家长端和教师端的业务规则全部由后端接口给，移动端只做展示，避免了规则在两端重复实现导致口径不一样。
- 代价我也如实说：跨平台方案在极致的原生体验和部分原生能力上会有折中，但我们的场景基本不触及这些边界。

佐证材料：`docs/thesis/03-第2章` §2.2；`docs/thesis/04-第3章` §3.2。

### Q4. 为什么引入 Flyway？不手工维护建表脚本不行吗？

考察意图：考察对数据库可演进性、环境一致性的工程意识。

回答要点：
- 手工维护建表脚本最大的问题是「环境漂移」：开发、测试、生产的库结构各自被人手动改过，时间一长就对不上，出问题很难定位。
- Flyway 把结构变更变成带编号的迁移脚本，应用启动时按序自动执行，每个环境跑的是同一套脚本，结构自然一致。
- 我们实际用了三个增量迁移：V6 加高价值查询索引、V7 加「单条待审核退费」的约束、V8 加流失预警跟进表；并且迁移脚本都写成幂等的，支持存量库平滑升级。
- 生产首次部署时还有个小技巧：先用建表脚本把库建到基线状态，再用 baseline 机制记为基线版本，之后只跑增量。这保证存量库不会被重复建表脚本冲突。
- 一句话：Flyway 让数据库的演进可审计、可回放，这是我要它而不是要个建表脚本的原因。

佐证材料：`docs/deployment-2026-09-10.md` §4「关键设计验证」；迁移脚本 `backend/src/main/resources/db/migration/V6/V7/V8`；`docs/thesis/03-第2章` §2.4。

## B 类：核心难点

### Q5. 并发一致性到底怎么保证的？是不是只加了个乐观锁？

考察意图：这是最容易被追问的点，考察是否真懂而不是背术语。

回答要点：
- 不是单一手段，是一套组合拳，而且分场景。
- 第一层是数据库事务：课时扣减要写考勤记录、改账户余额、写课时流水三张表，这三步必须在同一个事务里，任一步失败整体回滚，中间状态对外不可见。
- 第二层是乐观锁：课时账户带版本号，更新时用「编号加版本号」做条件，版本对不上就更新 0 行，直接返回冲突让人刷新重试，不允许静默覆盖。
- 第三层是数据库约束兜底：比如「同一笔报名最多一条待审核退费」这条，是用生成列加唯一索引在数据库层面保证的，就算应用层有漏洞也越不过去。
- 第四层是业务规则的前置校验：比如已批准请假的学员不许被改成到课，从规则上杜绝「请假不扣课时」被绕过。
- 一句话：乐观锁负责防并发覆盖，事务负责原子性，数据库约束负责兜底，业务校验负责守住规则，四者缺一不可。

佐证材料：`docs/12-核心算法设计文档.md` §4.3；`docs/thesis/05-第4章` §4.1.2/§4.3.2；`docs/thesis/04-第3章` §3.4（V7 单待审核退费约束）。

### Q6. 课时扣减怎么保证不重复扣？老师改了考勤状态怎么办？

考察意图：考察对幂等和回冲的理解，这是账实一致的关键。

回答要点：
- 幂等：同一学员同一课次只保留一条有效考勤。重复提交考勤时，系统先查到已有记录，走的是「更新已有状态」而不是「再插一条再扣一次」，所以不会重复扣。
- 回冲：如果老师修改了已提交的考勤状态，比如原来标缺勤后来证明是请假，系统不是直接改数字，而是先把原来那笔扣减回冲掉，再按新状态重新计算，整个过程仍然在同一个事务里。
- 防重复回冲：回冲时会把原记录的扣减量标记置零，这样即使再触发一次回冲，也不会重复退课时。
- 到课/迟到会正常扣课时；余额不足时最多扣到 0、不会扣成负数，并在流水中标注「课时不足，扣至 0」。若账户余额已经为 0，系统会拒绝该次扣减并提示先续费（当前未实现欠费记账）。

佐证材料：`docs/12-核心算法设计文档.md` §4.1/§4.2；`docs/thesis/05-第4章` §4.3.2；测试用例 T11~T14（`docs/thesis/06-第5章` 表 5.4）。

### Q7. 排课冲突怎么检测？会不会漏判？

考察意图：考察冲突检测的完整性，尤其是「旧课次是否参与判断」这种细节。

回答要点：
- 核心是时间区间交叉判断：两个时间段有交叉，当且仅当一个的开始早于另一个的结束，且一个的结束晚于另一个的开始。
- 我们在这个公式上覆盖五个时间交叉维度：同一老师、同一教室、同一教室的教室预约（考试、教研活动等非常规占用）、同一班级、以及跨班学员的时间冲突。这里要澄清一点：容量校验不属于冲突检测，而且只有智能（自动）排课在选教室时按「教室容量大于等于班级设计人数上限」过滤——注意是设计上限不是当前人数，避免以后报名满了才发现坐不下；手动排课只拦时间冲突，不拦容量。
- 漏判的关键防线在一个细节上：检测时只把「待上课」和「已完成」的课次算进去，已取消和已调课的旧课次不参与。否则会出现一个很隐蔽的误判——调课之后空出来的那个时间段，因为旧课次还挂在那里，被判成仍有冲突。补充说明：取消课次当前走的是逻辑删除，软删记录本就不在有效状态范围内，所以「旧课次不参与」在取消与调课两条路径下都成立。
- 批量排课和自动排课时，我们采用「全部通过才保存」的策略，避免部分成功部分失败让教务看不懂。

佐证材料：`docs/12-核心算法设计文档.md` §2.2/§2.3/§2.4；`docs/thesis/05-第4章` §4.2.1；测试用例 T07（`docs/thesis/06-第5章` 表 5.3）。

### Q8. 拖拽调课的并发问题，你是怎么发现并解决的？

考察意图：这是本系统最有代表性的难点，考察真实的问题定位能力。

回答要点：
- 问题是测试阶段被 QA 发现的。快速调课有个约束：不能改变课次状态，所以它不会翻转状态字段。
- 而原来的乐观条件只有「编号加状态」。课次状态没变，那这个条件对两名教务同时拖同一节课就是无效的，第二笔更新照样能改，等于第一笔被静默覆盖了。
- 解法是往乐观更新条件里再追加「原日期、原开始时间、原结束时间」这三个条件。并发第二笔更新时，旧时间已经对不上了，更新 0 行，接口返回冲突提示，让后改的人刷新重试。
- 我们还专门加了一条回归测试，去捕获这次更新的条件参数，防止将来有人又把它改回「只有编号加状态」的弱保护。
- 这件事给我的收获是：并发保护的强度取决于条件够不够「唯一标识这一次改动」，光靠状态往往不够。

佐证材料：`docs/thesis/05-第4章` §4.2.2（含 CAS 代码片段）；`docs/thesis/06-第5章` §5.3.1 与测试用例 T09。

### Q9. 老师薪资为什么不会被篡改？核算结果怎么保证可信？

考察意图：考察状态机、唯一约束与留痕机制。

回答要点：
- 三道保障。
- 第一是核算口径可信：薪资按「课次到班级、班级到课程、课程到薪资规则」的映射自动算，而且只有已完成、且存在到课或迟到考勤的课次才计入薪资，仅请假或仅缺勤的课次不计薪，避免「有课次没上课也算钱」这种口径和实现脱节。
- 第二是状态机加并发控制：薪资单走核算、确认、发放、撤销四个状态，关键流转都用乐观条件更新，比如只有「核算」状态才能被确认；同一老师同一月份只允许一张有效结算单，这是数据库唯一约束兜底的。
- 第三是变更留痕：如果一张薪资单已经确认，之后那段时间的课次或考勤又被追溯修改了，我们不去覆盖原单金额，而是按变更前后的差额写一条调整记录；老师实发等于原金额加上所有调整记录之和。需要整单作废，也只能走「撤销后重新核算生成新单」的路径。
- 一句话：金额不是被人改出来的，是算出来的；已确认的数字改不了，只能追加调整记录，任何变化都有迹可循。

佐证材料：`docs/12-核心算法设计文档.md` §6.4/§6.5/§6.6；`docs/thesis/04-第3章` §3.3.4（薪资状态流转图）；`docs/thesis/05-第4章` §4.4.2。

### Q10. 流失预警为什么用规则而不是机器学习？

考察意图：考察需求判断能力，以及是否清楚规则与模型的适用边界。

回答要点：
- 首要原因是可解释性和可用性。我们的使用者是教务人员，他需要的是「这个孩子为什么有风险、我该做什么」，而不是一个没有解释的概率值。
- 我们的五因子规则里，每个学员的风险分都能还原成是哪几个因子、命中了什么原因，教务看了能直接决定是打电话、还是提醒续费。黑盒模型做不到这一点，会给一线使用带来障碍。补充一点：五个因子中，异常出勤因子是预留开关、默认关闭，所以当前默认档实际生效的是前四个因子；被追问因子数时按这个口径答。
- 第二个原因是数据条件。这个系统还在数据积累阶段，而机器学习模型要靠足量、标注好的样本来训练，现在直接上模型，效果和可信度都不好保证。
- 第三是可维护性：规则能直接改参数、能直接测，符合我们「可解释、可实现、可测试」的设计原则。
- 我也把它说成是阶段性的选择：后续可以在规则打分的输出上再叠一层机器学习，同时保留规则做可解释的兜底。

佐证材料：`docs/thesis/05-第4章` §4.6.2；`docs/12-核心算法设计文档.md` §1；`docs/thesis/07-总结.md`（后续方向）。

### Q11. 流失预警会不会误报？怎么控制？

考察意图：考察规则设计的严谨性和对业务噪声的处理。

回答要点：
- 会，所以专门做了防误报规则，这也是规则化方案的优点——噪声能一条条怼回去。
- 第一条：学员所在班级最近根本没有排课的，不因为「沉寂了多久」而计分。否则一个班级放寒假，全班都会被误判成高风险。
- 第二条：已经批准请假的缺勤，不计入缺勤倾向。请假是正常的，不能当异常。
- 第三条：已经退班的学员不进预警名单，他已经流失了，预警要盯的是还在班上的。
- 补充：五个因子中异常出勤因子是预留开关、默认关闭，当前默认档只生效前四个因子，这也在一定程度上缩小了误报面。
- 另外预警名单支持按班级、课程、风险档筛选，也支持一键站内触达家长和导出 Excel，跟进状态形成闭环，避免预警出一条就没人管。

佐证材料：`docs/thesis/05-第4章` §4.6.2；测试用例 T16、T17、T18（`docs/thesis/06-第5章` 表 5.5）。

### Q13. 为什么要容器化部署？是不是为了显得高级？

考察意图：考察部署形态的工程动机，而不是堆工具。

回答要点：
- 动机很实际，主要是三条。
- 一致性：把数据库、反向代理、Web、后端应用编排成固定拓扑，每个环境跑的是同一套编排文件，环境差异被压到最小。
- 可恢复：容器都配置成随宿主机重启自动拉起，配合数据卷持久化数据库和上传附件，机器重启后能自动恢复，不用人上去手工启一遍。
- 可验证：部署流水线设了测试门禁、登录接口冒烟探测和容器健康检查，任何一步失败就阻止发布，发布这件事本身是可验证的。
- 还有个附带好处是可追溯：镜像带版本标签，结合版本信息端点能查到当前线上跑的是哪个镜像。
- 一句话：容器化不是为了好看，是为了让「部署」这件事可重复、可恢复、可验证。

佐证材料：`docs/deployment-2026-09-10.md` §1/§3/§5；`docs/thesis/04-第3章` §3.5。

### Q14. 可观测性具体做了什么？

考察意图：考察线上问题定位能力，是不是「部署完就不管了」。

回答要点：
- 三个层面。
- 健康与就绪探针：对外提供健康检查端点，容器和负载层都能据此判断应用是否就绪。
- 指标暴露：通过 Actuator 暴露指标，实际部署时指标端点有 265 条指标；除了通用指标，我们还放了业务指标，比如待处理退费数量、登录失败计数（区分凭证错误和账号锁定）。
- 关联日志：请求带关联标识，出问题能顺着一条链路把日志串起来，便于定位。
- 版本信息：单独一个端点返回当前镜像标签，发布之后能确认线上是哪个版本。
- 一句话：探针负责「活没活着」，指标负责「健康不健康」，日志和版本负责「出了事能查、能对上号」。

佐证材料：`docs/deployment-2026-09-10.md` §5「可观测性」；`docs/thesis/06-第5章` §5.3.3。

## D 类：局限与反思

### Q15. 支付和短信是模拟的，那你这个系统算不算没做完？

考察意图：考察是否诚实，以及是否清楚范围边界。

回答要点：
- 我如实说：是的，支付是模拟支付，短信通知也没有接真实的短信服务商，目前是站内通知。这两项都按「后续方向」如实写在论文里，没有当成已完成。
- 但要分清范围：任务书对这两项没有强制要求接真实网关，系统当前的缴费、退费、账实联动、通知推送这些业务逻辑是完整且经过验证的，缺的是「最后一公里的外部通道对接」，不是业务能力缺失。
- 而且系统在设计上留了扩展点：通知这块已经有外发通道的抽象，后续接第三方支付网关和短信服务商，以适配器方式接入就行，业务逻辑不用重写。
- 一句话：业务闭环是通的，外部通道是待接的，这一点我不回避。

佐证材料：`docs/thesis/07-总结.md`（不足与后续方向）；`docs/thesis/04-第3章` §3.3.1 时序图（标注模拟支付）；`docs/acceptance-matrix-2026-07-19.md`「已知限制」。

### Q16. 当前是单机部署，那你的并发控制还有意义吗？

考察意图：考察是否理解单机与分布式的差异，以及设计是否面向演进。

回答要点：
- 有意义，但我要如实说清楚边界。
- 在单机范围内，来自多个用户、多个浏览器会话的并发请求是真实存在的，乐观锁和事务解决的就是这类并发下的账实一致，这一点在测试里验证过。
- 但我也承认：报名决策快照目前是在单机内存里做版本令牌校验，令牌 5 分钟过期，一旦后端扩展成多实例，这份单机内存状态就没法共享了，这是当前真实存在的短板。
- 后续的做法是把版本令牌校验迁到分布式缓存，配合共享的并发控制，才能支撑多实例水平扩展。这一点论文里也写成了后续方向。
- 一句话：现在的并发控制对单机场景是有效的，但要上多实例，单机内存里的令牌校验和共享控制必须先改造。

佐证材料：`docs/thesis/07-总结.md`；`docs/thesis/05-第4章` §4.1.1（单机内存中的报名快照版本令牌，5 分钟过期）；`docs/thesis/04-第3章` §3.5（部署拓扑为单机编排）。

### Q17. 没有缓存的短板在哪？如果重做你会改什么？

考察意图：考察自我反思的深度和真实性。

回答要点：
- 先说短板。当前架构里没有引入分布式缓存，报名决策快照的版本令牌校验只在单机内存里，多实例时不能共享；另外我们没有做压力测试，所以性能层面我只能给定性判断，说「交互流畅」，不能说具体支撑多少并发、响应多少毫秒，这个如果没有实测数据是不能讲的。
- 如果重做，我会按优先级改三件事。第一，数据访问层面把热点读和高频统计结果缓存起来，把报名快照的版本令牌校验迁到分布式缓存，让多实例部署成为可能。第二，补一套压力测试，把性能从定性变成定量，用数据说话。第三，在流失预警的规则打分之上升级机器学习模型，同时保留规则做兜底解释。
- 另外工程上还有一个教训我会固化下来：部署流程要强制校验构建产物的新鲜度。这次的移动端旧产物问题就是没有这一步造成的。

佐证材料：`docs/thesis/07-总结.md`；`docs/thesis/06-第5章` §5.3（未涉及压测）；`docs/deployment-2026-09-10.md` §8（产物新鲜度教训）。

### Q18. 演示数据是固定日期，看板会不会出问题？

考察意图：考察是否清楚演示数据的口径陷阱，这是很容易被现场抓的点。

回答要点：
- 会，而且我们已经识别到了。演示库是固定日期的种子数据。
- 一个典型现象是：如果「当月」缴费为 0 但有退费留存，运营看板的月度营收口径就会显示成负值。这不是系统算错了，而是统计口径的正常结果——营收等于收费减退费。
- 处置办法很直接：答辩前重置数据或让当月有缴费记录，避免出现容易被误读的负营收。
- 还有一个类似的口径问题是「在册学员」：看板统计的是去重后的在册学员数，之前统计的是在班人次，12 个学员里有 3 人各报了两个班，人次就多算了。这个问题后来用去重统计修正了，看板现在和学员列表一致。

佐证材料：`docs/deployment-2026-09-10.md` §7；`docs/ui-test-report-final-2026-09-10.md` 第五节 ISSUE-001。

## E 类：工作量与原创性

### Q19. 这个系统哪些是你自己写的？AI 辅助到什么程度？（必须如实回答）

考察意图：确认工作量归属与原创性，考察诚信。

回答要点：
- 我如实讲，不夸大。
- 架构设计和技术选型是我做的：前后端分离的 B/S 架构、16 个后端模块的划分、37 张表的数据模型、五类角色的权限体系、以及那几个核心难点的解法，包括报名决策快照加版本校验、拖拽调课的复合乐观条件、薪资的状态机加调整记录、流失预警的五因子规则。业务规则和数据模型是这门课真正的产出，这部分是我主导并逐条定下来的。
- AI 辅助主要在编码实现层面：写 CRUD、写页面、写测试用例这些重复度高的部分，我用 AI 辅助生成，然后逐个人工审阅、补业务逻辑、跑测试验证。也就是说，AI 帮我提了效率，但每一段逻辑我都读懂、都能解释，测试也是真实跑过的。
- 我不会说「全部是我一个人手写的」，那不符合事实；我也不会说「AI 做的」，因为架构和业务规则这些最难、最核心的部分是我做的。
- 可以佐证：系统里有 16 个后端模块、37 张表，这些设计的取舍我都能现场解释；如果老师对某个实现有疑问，我可以直接打开对应代码说明。
- 一句话：AI 是我用来提高编码效率的工具，架构设计、业务规则和技术决策是我自己的工作量。

佐证材料：`docs/archive/test-reports/taskbook-compliance-v1.2-2026-09-07.md` 一、二节（16 模块、37 表、五大角色 35+ 子项的逐条实现证据）；`docs/thesis/05-第4章`（核心难点的设计与代码）；各测试报告（用例为真实执行）。
