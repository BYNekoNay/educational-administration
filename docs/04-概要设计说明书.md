# 概要设计说明书

> **版本状态**：v0.9 规划版，基于 `03-软件需求规格说明书.md` 编制，尚未与实际代码和测试结果核对，详见 `00-文档说明.md`。

## 1. 设计目标与原则

### 1.1 设计目标

在满足学员家长、授课教师、教务管理员、财务管理员、超级管理员五类角色需求的前提下，构建一个结构清晰、易于维护、可扩展的艺术培训机构教务管理平台。系统重点解决报名缴费、课程班级、智能排课、课堂考勤、课时扣减、学情记录、收费退费、教师薪资和运营统计等业务问题。

### 1.2 设计原则

- **终端匹配岗位场景**：家长和教师以移动端高频轻操作为主，采用 uni-app；教务、财务和超级管理员以 PC 后台复杂管理为主，采用 Vue3 + Element Plus；
- **角色边界清晰**：不同岗位只访问与职责相关的菜单、接口和数据；
- **业务闭环优先**：优先打通报名、排课、考勤、课时、收费、薪资和统计链路；
- **数据可追溯**：课时、收费、退费、薪资等关键数据通过流水和日志保留历史；
- **统一后端接口**：移动端与管理后台共用 Spring Boot REST API，避免业务规则分散。

## 2. 总体架构

系统采用前后端分离架构，前端分为 **uni-app 移动端** 和 **Vue3 管理后台** 两个工程，后端统一提供 REST API。

```
┌──────────────────────────────────────────────┐
│ 表现层 A：uni-app 移动端                       │
│ 家长端 / 教师端，可发布 H5、微信小程序或 App       │
└───────────────────┬──────────────────────────┘
                    │ HTTPS + JWT
                    │
                    ├──────────────────────────┐
                    │                          │
┌───────────────────▼──────────────────────────▼┐
│ 业务层：Spring Boot RESTful API                 │
│ 用户权限 / 学员 / 课程 / 排课 / 考勤 / 财务 / 统计  │
└───────────────────▲──────────────────────────▲┘
                    │                          │
                    │ HTTPS + JWT              │
┌───────────────────┴──────────────────────────┐
│ 表现层 B：Vue3 + Element Plus 管理后台          │
│ 教务端 / 财务端 / 超级管理员端                   │
└──────────────────────────────────────────────┘
                    │
                    ▼
┌──────────────────────────────────────────────┐
│ 数据层：MySQL 8.0 + Redis                      │
│ 业务数据、财务数据、日志数据、缓存、提醒、热点数据   │
└───────────────────┬──────────────────────────┘
                    │
                    ▼
┌──────────────────────────────────────────────┐
│ 规则/统计层：排课冲突检测、课时扣减、薪资核算、统计聚合 │
└──────────────────────────────────────────────┘
```

> 说明：uni-app 移动端与 Vue3 管理后台是两个并列终端，二者都直接调用 Spring Boot REST API，不存在移动端经过管理后台转发业务请求的关系。

- **uni-app 移动端**：承载家长端和教师端，适合手机端查看课表、接收通知、课堂考勤、作业点评等即时操作；
- **Vue3 管理后台**：承载教务、财务和超级管理员端，适合 PC 端批量管理、复杂表格、排课、统计看板和报表导出；
- **业务层**：Spring Boot 提供统一 REST API，处理鉴权、权限、参数校验、业务规则、事务控制；
- **数据层**：MySQL 保存业务数据，Redis 用于缓存、验证码、课表提醒、热点统计等；
- **规则/统计层**：封装排课冲突检测、课时扣减、薪资核算、统计聚合和报表导出逻辑。

## 3. 模块划分

### 3.1 终端模块

| 工程 | 角色 | 模块说明 |
|---|---|---|
| mobile-uniapp | 家长端 | 课程套餐、在线报名、缴费记录、课表、学情、课时余额、通知 |
| mobile-uniapp | 教师端 | 我的课表、调课申请、课堂考勤、作业发布、学情点评、课时统计 |
| admin-web | 教务端 | 课程管理、班级管理、智能排课、调课管理、学员档案、报名审核、考级管理 |
| admin-web | 财务端 | 收费台账、续费管理、退费审核、课时消耗、薪资结算、营收统计 |
| admin-web | 管理端 | 用户管理、角色权限、机构配置、公告管理、全局看板、操作日志 |
| 公共能力 | 全端 | 登录、Token、请求封装、文件上传、权限校验、错误提示 |

### 3.2 后端模块

| 模块 | 职责 | 关键实体 |
|---|---|---|
| 用户与权限模块 | 登录认证、JWT、角色权限、账号状态 | user、role、permission |
| 学员模块 | 学员档案、家长关系、报名审核、转班退班 | student、parent_student、enrollment |

| 排课模块 | 课次生成、冲突检测、调课、教室预约 | schedule_lesson、classroom、room_booking |
| 考勤学情模块 | 签到、请假、缺勤、作业、课堂点评 | attendance、homework、learning_record |
| 财务模块 | 收费、续费、退费、课时账户、课时流水 | payment_record、refund_record、lesson_account、lesson_flow |
| 薪资模块 | 教师课时统计、代课系数、薪资结算 | salary_rule、teacher_salary |
| 考级模块 | 考级项目、报名、成绩、证书归档 | exam_level、exam_signup、certificate |
| 统计模块 | 招生、到课率、营收、课时、工作量统计 | statistics_snapshot、业务聚合查询 |
| 系统模块 | 机构配置、公告、通知、操作日志 | organization、notice、operation_log |

## 4. 技术选型说明

| 技术 | 选型理由 |
|---|---|
| Spring Boot | 简化后端配置，适合快速构建 REST API 和业务服务 |
| MyBatis-Plus/MyBatis | 支持通用 CRUD 和复杂统计 SQL，减少样板代码 |
| MySQL 8.0 | 事务能力强，适合课时、财务、薪资等一致性数据 |
| Redis | 支撑缓存、验证码、提醒、热点统计等能力 |
| JWT | 适合前后端分离的无状态登录鉴权 |
| uni-app | 一套代码可发布 H5、微信小程序和 App，适合家长/教师移动端场景 |
| Vue3 | 适合构建管理后台，组合式 API 便于复用复杂表格和表单逻辑 |
| Element Plus | 提供成熟中后台组件，适合教务、财务、管理后台 |
| ECharts | 满足经营统计、课时趋势、到课率等图表展示 |
| EasyExcel/PDF 工具 | 支撑收费、课时、薪资和营收报表导出 |

## 5. 部署架构

```
移动端用户
   │ H5/小程序/App
   ▼
uni-app 构建产物或小程序包
   │ HTTPS
   ▼
Nginx / 小程序平台

PC 管理人员
   │ 浏览器
   ▼
Nginx（Vue3 管理后台静态资源 + 反向代理）
   │
   ▼
Spring Boot 应用
   │
   ├── MySQL 8.0
   └── Redis
```

毕业设计演示阶段可采用 uni-app H5 端 + Vue3 管理后台 + Spring Boot 单机部署；如需要展示小程序效果，可使用微信开发者工具运行 uni-app 小程序端。

## 6. 关键设计决策

### 6.1 移动端与后台职责分离

家长和教师端只保留手机端自然需要的轻量操作，如查看课表、考勤、学情、课时和通知；复杂的课程、排课、财务、权限、统计配置集中在 PC 管理后台完成。

### 6.2 排课冲突检测策略

排课时对教师、教室、教室预约、班级、学员五个维度进行时间交叉检测，并校验教室容量是否满足班级设计容量上限。若已有课次或预约满足 `existing.start < new.end AND existing.end > new.start`，则判定冲突并返回冲突明细；已取消或已调课的旧课次不参与判断。毕业设计阶段采用“自动检测 + 人工调整”方式，不追求全局最优排课。详细规则见 `12-核心算法设计文档.md` §2。

### 6.3 课时账户与课时流水

学员购买课程后生成或更新课时账户；每次到课或按规则应扣课时的考勤记录都会产生课时流水。课时余额只通过流水驱动变化，避免直接修改导致历史不可追溯。

### 6.4 薪资结算规则

教师薪资根据已完成课次、有效考勤确认、主讲课时、代课课时、课时单价和代课系数计算，核算时记录计算截止的数据快照时间点。薪资单生成后可由财务确认，确认后的结算单禁止直接覆盖；若需修改，通过 `salary_adjustment` 调整记录叠加差额，或将结算单状态置为"已撤销"后重新核算生成新单，保证财务数据可追溯。

### 6.5 数据统计设计

招生人数、到课率、课时消耗、营收、课程盈利、教师工作量等指标优先通过 MySQL 聚合查询实现；高频看板可使用统计快照表或 Redis 缓存。管理后台图表统一使用 ECharts，后端返回时间序列、分类汇总和指标卡片数据。

### 6.6 权限与审计

登录后签发 JWT，后端拦截器解析用户身份和角色。系统按角色限制菜单和接口访问；收费、退费、薪资、权限、公告等敏感操作写入操作日志，便于审计和问题追踪。
