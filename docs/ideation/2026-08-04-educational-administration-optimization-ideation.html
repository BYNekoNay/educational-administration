Evidence

Grounding Context

系统形态：Spring Boot + MyBatis + MySQL 后端，Vue 管理端，UniApp H5/移动端，Docker Compose 部署到阿里云 ECS，镜像经 GitHub Actions 和 ACR 发布。

已有基础：JWT、BCrypt、数据库角色校验、家长数据范围、审计日志、较多后端与管理端测试，以及已经可访问的生产环境。

主要风险：生产配置仍允许开发默认值；数据库初始化依赖空卷；只有 MySQL 健康检查；没有明确备份、恢复、迁移和回退闭环。

体验与质量：H5 报名存在串行请求扇出，移动端没有测试；CI 构建与发布没有执行现有测试，线上诊断主要依赖日志与前端 toast。

判断：当前最需要的不是新增模块，而是把现有系统从“能运行”提升到“能证明安全、能证明数据正确、能证明本次发布可用，并且出现问题能恢复”。

1. 生产安全配置契约

P095% confidenceLow-Medium
Description
生产环境不再继承可运行的数据库密码、JWT 密钥和宽松来源默认值。启动时校验密钥强度、必需配置和精确来源白名单，发现开发回退值就拒绝启动；上传同时从扩展名判断提升到内容类型与文件头校验。
Axis
权限与数据保护
Basis
direct: application.yml 中仍有 ${DB_PASSWORD:123456} 与开发 JWT 回退值；application-prod.yml 未覆盖这些安全配置；JwtUtil 会补齐短密钥而不是拒绝。上传准入主要依赖文件扩展名。
Rationale
这把安全从“部署人员记得配置”变成系统自身可验证的生产属性，成本低、收益直接，并为后续 HTTPS、会话与文件安全治理建立底线。
Downsides
首次启用会暴露现有环境变量缺口，可能导致一次部署失败；需要建立密钥生成、轮换和紧急撤销的操作说明。

2. 备份、恢复与定期演练

P096% confidenceMedium
Description
为 MySQL 与上传附件建立加密备份、保留期、异地副本和失败告警；按固定周期在隔离环境真实恢复，并用登录、课时余额、退款记录、附件读取等检查证明备份可用，同时明确可接受的数据丢失窗口和恢复时长。
Axis
CI/CD、生产韧性与恢复
Basis
direct: 生产 Compose 仅通过命名卷持久化 MySQL 与 uploads，部署工作流没有备份或恢复命令；仓库中的重置脚本包含直接重建数据库的路径。现有证据只能证明“数据落盘”，不能证明“数据可恢复”。
Rationale
资金流水、课时账户、排课和教育附件是不可轻易重建的数据。恢复演练比单纯生成备份文件更能降低单机 ECS、误操作和升级事故的真实风险。
Downsides
需要对象存储或额外备份空间、加密密钥管理和定期演练时间；恢复检查必须避免把真实隐私数据扩散到不受控环境。

3. 版本化数据库迁移与约束治理

P093% confidenceMedium
Description
用 Flyway、Liquibase 或等价机制给每次结构与数据变更编号，增加迁移前检查、迁移后不变量校验和失败补偿说明。同步审查财务、退款、课时和归属关系中的唯一约束、外键或应用级替代约束，以及已经出现内存分页和并发窗口的查询。
Axis
核心业务一致性与数据库演进
Basis
direct: Compose 的 /docker-entrypoint-initdb.d 初始化只在新数据卷生效；仓库里同时存在条件式迁移 SQL。证据抽查还发现部分资金相关表未声明数据库外键，退款查询存在全量加载后再分页的路径。
Rationale
当前部署已经发生过“数据库为空但容器正常”的事故。版本化迁移和约束治理能把数据库状态纳入发布事实，并优先保护付款、课时、退款与排课这些高价值数据。
Downsides
首次基线化需要确认线上实际 schema，并清理不满足新约束的历史数据；回退应以向前修复或补偿为主，不能假设所有迁移都可逆。

4. 可验证发布门禁与明确回退流程

P092% confidenceMedium
Description
把发布成功从“容器已启动”改为“镜像可追溯、数据库版本正确、后端 readiness 正常、管理端与 H5 可访问、登录/API 冒烟通过”。任何门禁失败就停止晋级、保存诊断，并执行预先验证的回退流程；在数据库迁移不可逆时明确采用向前修复，而不是盲目自动回滚。
Axis
CI/CD、生产韧性与恢复
Basis
direct: 当前远程步骤最终执行 docker compose pull && docker compose up -d --remove-orphans && docker compose ps；Compose 只有 MySQL healthcheck，未发现后端 Actuator/readiness，也没有发布后业务探针或回退命令。部署修复还分散在不同分支/工作树。
Rationale
容器运行不等于教务业务可用。最小发布门禁能把近期 ACR、SSH、镜像、SQL 权限问题沉淀为以后每次发布都会执行的能力。
Downsides
发布会比当前多几分钟，冒烟账号与种子数据需要治理；回退规则必须区分无状态镜像失败和已改变数据库状态的失败。

5. 关键角色旅程进入 CI

P194% confidenceMedium
Description
保留快速单元测试，同时把家长报名/缴费、教师考勤、教务排课或调课、财务退款、管理员权限变更定义为稳定的跨端旅程。每次合并先跑后端与管理端测试，再跑首批移动端请求/会话测试和关键旅程；只有通过才允许构建生产镜像。
Axis
测试、可观测性与可维护性
Basis
direct: 仓库已经有五角色 curl 验收和大量后端/管理端测试，但部署工作流没有调用 mvn test、Vitest 或验收脚本，Docker 后端构建还跳过测试编译；mobile-uniapp 没有测试脚本或测试文件。
Rationale
这是把已有测试资产接回交付链，而不是从零追求覆盖率。它直接保护最容易产生业务损失的跨角色流程，并为 H5 后续优化提供安全网。
Downsides
需要确定可重复的种子数据、隔离测试环境并控制耗时；端到端测试如果过度依赖 UI 细节会变得脆弱，应以 API 和关键结果为主。

6. 业务可观测性最小闭环

P191% confidenceMedium
Description
先建立请求关联 ID、结构化日志、后端健康与就绪端点、版本信息和少量业务指标。首批只覆盖登录异常、报名/支付失败、退款积压、课时 CAS 失败、排课冲突和通知连接异常，并为每类信号设定可行动的告警条件。
Axis
测试、可观测性与可维护性
Basis
direct: application-prod.yml 主要只有包级日志配置；仓库未发现 Actuator、Prometheus、readiness 或 liveness；移动端失败主要被归一为 toast，管理端/移动端诊断仍大量依赖 console。
Rationale
发布门禁只能说明上线时可用，可观测性解决上线后“谁受影响、卡在哪一步、是否与本次版本有关”。用业务指标而非海量基础设施指标起步，能控制成本。
Downsides
日志与指标需要避免学生、家长和财务隐私；告警阈值初期可能产生噪声，需要明确责任人和逐步校准。

7. H5 报名决策快照

P188% confidenceMedium
Description
为家长报名提供一次请求的决策快照：课程、可选班级、名额、当前报名状态、学生时间冲突和占位到期时间在同一响应中返回，并携带快照版本供提交时校验。H5 不再逐课程串行拼接多个时点的数据。
Axis
后台与 H5 工作流及前端质量
Basis
direct: mobile-uniapp/src/pages/parent/enrollment.vue 会遍历课程，逐个加载班级并检查报名状态；后端同时存在容量重查和报名占位语义。当前结构既产生请求扇出，也可能让用户基于不同时间点的状态做决定。
Rationale
这是少数同时改善 H5 速度、状态一致性和用户决策质量的产品改动。它比先做视觉调整更直接地影响家长的高价值流程。
Downsides
需要新增聚合读模型并明确快照过期、权限与提交校验；响应不能变成无边界的大对象，应严格围绕报名决定。

Critical cut

Rejection Summary

#IdeaReason Rejected
1用途限定会话与一次性票据令牌暴露有证据，但全面重做浏览器会话和文件/SSE 票据超出当前必要范围。
2动作与数据范围策略中心方向可靠，但现有 RBAC 与归属校验已提供基础，紧迫性低于生产配置和交付风险。
3完整文件保留与下载审计边界内容校验被并入安全基线；保留期和下载审计缺少明确业务证据。
4统一不可变教务总账现有课时与退款流水支持加强对账，但不足以证明横跨收费、课时、退款和薪资的重写值得当前成本。
5通用交易幂等内核退款并发窗口支持定点幂等与唯一约束，不支持为所有命令建设通用内核。
6统一排课资源预订引擎现有冲突检查复杂，但没有规模故障证据；领域重构成本较高。
7业务不变量异常运营队列适合作为数据治理后续，但尚无异常发生量和处理责任模型。
8全自动回滚收缩为明确回退流程；有状态数据库迁移下盲目自动回滚不安全。
9签名发布清单与主机主动收敛对单台 ECS 来说引入主机代理和签名协议过重，当前健康门禁收益更高。
10全服务健康模型已合并到“可验证发布门禁”。
11角色任务驾驶舱现有首页已覆盖高频入口，缺少用户研究或漏办数据证明应立即重做信息架构。
12后台异常运营台异常类型存在，但人员责任、量级和处理时限尚未建立。
13移动端离线命令日志弱网推理合理，但没有事故/重试证据支撑新增冲突合并和 outbox 语义。
14跨端 API 与会话单一来源两个客户端确有重复，但目前证据只显示少量 token/401 逻辑，不足以支撑广泛契约层。
15正式前端性能预算缺少当前包体、首屏耗时和接口延迟基线；先修复已知报名请求扇出。
16完整发布证据包其测试、镜像、迁移和探针部分已分别合并进数据库、CI 和发布门禁方向。
17拆分 821 行排课服务证据充分，但属于降低维护成本的后续工作，当前价值低于生产与数据控制。
18专项 docs/solutions 与策略文档特定目录缺失不等于项目没有文档；仓库已有大量审计、计划和报告。
19部署分支/工作树单独治理项目作为发布门禁的前置清理处理，不单列为战略方向。
20数据库约束与索引专项已合并到“版本化数据库迁移与约束治理”。
