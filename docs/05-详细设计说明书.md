# 详细设计说明书

> **版本状态**：v1.0 正式版，已与实际代码和测试结果核对，验收日期 2026-07-19。

## 1. 概述

本文在概要设计基础上，进一步说明数据库表结构、核心业务流程、关键算法规则、接口清单、异常处理与安全设计，为后端、前端、测试和论文撰写提供详细依据。

## 2. 数据库设计

### 2.1 设计说明

- 存储引擎：InnoDB；字符集：utf8mb4；
- 命名规范：表名和字段名使用小写下划线命名；
- 通用字段：核心表包含 `id`、`create_time`、`update_time`、`is_deleted`；
- 财务、课时、薪资等关键数据通过流水表或结算表保留历史；
- 涉及课时余额、收费退费、薪资确认的操作必须使用事务。

## 4. 关键业务流程详细设计

### 4.1 报名缴费与课时开通

```
1. 家长选择课程套餐并提交报名申请；
2. 教务审核学员信息、课程和意向班级：
   - 审核通过仅记录"意向分班"，校验意向班级 class_student 当前人数 < class_group.max_student_count，
     不通过则提示改选班级，通过则将 enrollment.status 置为"待缴费"，不立即写入 class_student；
   - 系统对"待缴费"状态设置留位时限（建议 24-72 小时，机构可配置），超时未缴费自动转为"已失效"并释放名额；
3. 财务登记收费或家长在时限内完成模拟缴费；
4. 写入 payment_record（关联 enrollment_id）；
5. 创建或更新 lesson_account；
6. 写入 lesson_flow 购买流水（source_type=1, source_id=payment_record.id）；
7. 缴费成功后正式写入 class_student，enrollment.status 置为"已完成"，并再次校验班级人数上限（防止同一时限内多个家长并发缴费超过容量，超过则转入候补或提示教务加开班级）；
8. 通知家长报名成功并展示课时余额。
```

> 说明：第2步与第7步的两次班级人数校验，分别对应"审核占位"和"缴费确认占位"两个环节，避免审核通过后无限期占用名额，也避免并发缴费导致班级超员。


### 4.2 智能排课与冲突检测

```
1. 教务选择班级、教师、教室、日期范围、周期和时间段；
2. 系统生成候选课次；
3. 检查教师、教室、班级、学员、教室预约五个维度是否时间交叉（详见 §5.1）；
   查询范围仅限 schedule_lesson.status 为"待上课"或"已完成"的课次，已取消/已调课的旧课次不参与冲突判断；
4. 无冲突则批量写入 schedule_lesson；
5. 有冲突则返回冲突明细，教务手动调整；
6. 排课成功后生成教师和家长端课表。
```

#### 4.2.1 手动调课子流程

```
1. 教师在课表中对某课次发起调课申请（写入 schedule_adjust_request，状态"待审核"），或教务直接发起手动调课；
2. 教务审核调课申请：
   - 审核前对申请中的新时间/新教师/新教室，复用 §5.1 冲突检测规则（不含原课次自身）；
   - 通过：原课次 schedule_lesson.status 改为"已调课"，新建目标课次并设置 source_lesson_id 指向原课次，
     schedule_adjust_request.status 置为"已通过"；
   - 驳回：schedule_adjust_request.status 置为"已驳回"，原课次不变；
3. 调课结果生成通知，推送给受影响的学员家长和教师（见 §4.1 note 与 09 接口 `/api/edu/schedule-adjust-requests`）。
```


### 4.3 课堂考勤与课时自动扣减

```
1. 教师进入课次并加载班级学员；
2. 教师提交考勤状态；
3. 系统校验 attendance(lesson_id, student_id) 是否已存在：
   - 不存在：按新增流程处理；
   - 已存在（教师修改考勤状态）：先按原状态对应的扣减数额回冲 lesson_flow（写入一条 change_type=4 调整流水并加回余额），再按新状态重新计算扣减，全程同一事务；
4. 根据考勤状态和机构规则计算扣减课时；
5. 校验 lesson_account.remaining_lessons：
   - 余额充足（>= 扣减数额）：正常扣减；
   - 余额不足但 > 0 且考勤状态为"到课"（到课是刚性事实，不能像请假一样跳过）：允许扣至 0，差额部分标记为"待续费欠费"，同时立即触发续费提醒，不允许扣成负数；
   - 余额为 0：阻止提交该学员的"到课"考勤，提示先完成续费；
6. 扣减余额并写入 lesson_flow（source_type=3, source_id=attendance.id）；
7. 剩余课时低于阈值时生成续费提醒。
```


### 4.4 退费流程

```
1. 教务或家长发起退费申请，写入 refund_record（关联 payment_record_id、enrollment_id，记录 applicant_id、applicant_role）；
2. 系统按 §5.4 公式计算建议退费金额，并校验该金额不超过"该 enrollment 累计已缴费金额 - 累计已退费金额"；
3. 财务审核：
   - 审核人若与 applicant_id 相同（即财务本人既是申请人又是审核人），系统强制转交其他财务人员复核，避免自审自批；
   - 审核通过或拒绝；
4. 审核通过后更新 refund_record.status，写入或更新负向 lesson_flow（source_type=2, source_id=refund_record.id）；
5. 调整 lesson_account.remaining_lessons（同一事务内使用 version 乐观锁更新）；
6. 若该学员在退费后课时不足以覆盖未来已排课次，联动将对应 class_student.status 置为"已退出"，并释放班级名额；
7. 记录操作日志。
```


### 4.5 教师薪资自动核算

```
1. 财务选择教师和结算月份，系统记录本次核算的 calc_snapshot_time（当前时间）；
2. 系统查询截至 calc_snapshot_time 当月已完成课次（含考勤确认，见 §5.3）与代课记录；
3. 按课程和薪资规则计算主讲工资与代课工资；
4. 加总奖金补贴和扣款；
5. 生成 teacher_salary，写入 calc_snapshot_time；
6. 财务确认后锁定结算单（status=2）。
```

#### 4.5.1 确认后课次/考勤变更的处理

若薪资单确认（status=2）后，其 calc_snapshot_time 之前统计过的课次或考勤被追溯修改（如课次由"已完成"改为"已取消"），系统不直接覆盖原薪资单，而是：

```
1. 教务/财务发起薪资调整；
2. 系统按变更前后差额生成 salary_adjustment 记录（关联 teacher_salary_id）；
3. teacher_salary.total_amount 不做覆盖式修改，实发金额 = 原 total_amount + 该薪资单下全部 salary_adjustment.adjust_amount 之和；
4. 若需要作废整张结算单，将 status 置为"已撤销"（4），并要求重新执行核算生成新单。
```

### 4.6 消息通知触发规则

对应 `03` FR-P-08，通知类型与触发条件如下：

| 通知类型 | 触发时机 | 接收对象 |
|---|---|---|
| 调课通知 | §4.2.1 调课审核通过后立即触发 | 受影响课次的学员家长、原/新授课教师 |
| 上课提醒 | 课次开始前固定提前量（建议 1 小时，机构可配置），由定时任务扫描当日待上课次触发 | 该课次学员家长、授课教师 |
| 课时不足提醒 | §4.3 考勤扣减后 `remaining_lessons` 低于阈值（机构可配置，默认 2 课时）时触发 | 该学员家长 |
| 报名留位到期提醒 | §4.1 留位时限届满前固定提前量（建议 4 小时）触发一次 | 发起报名的家长 |
| 考级通知 | 考级报名成功、成绩录入后触发 | 该学员家长 |
| 机构公告 | 管理端发布公告后立即触发 | 公告设置的接收范围 |


## 5. 核心算法与规则

### 5.1 时间冲突判断

```
existing.start_time < new.end_time AND existing.end_time > new.start_time
```

该条件适用于教师冲突、教室冲突、班级冲突、学员冲突和教室预约冲突五个维度。

- **边界说明**：两节课首尾相接（如 A 课 18:00-19:00，B 课 19:00-20:00）不算冲突，因为 `A.end_time(19:00) > B.start_time(19:00)` 不成立（等于不算大于），公式天然把"闭区间端点重合"排除在冲突之外。
- **学员维度**：同一学员通过 `class_student` 关联的不同班级课次之间也需做时间交叉检测（如同一学员报读的钢琴班和美术班被排到同一时段），防止学员被排入无法同时到场的课次。
- **状态过滤**：查询时应仅比对 `schedule_lesson.status` 为"待上课"（1）或"已完成"（2）的课次，已取消（3）与已调课（4）的旧课次不参与判断，否则调课后空出的时间段会被误判为仍有冲突。
- **教室预约冲突**：`room_booking` 用于非常规教室占用（如考试、教研活动），与 `schedule_lesson` 的常规排课占用共用同一时间交叉公式，两张表都需纳入教室维度的冲突查询范围。

### 5.2 课时扣减规则

| 考勤状态 | 默认扣课时 | 说明 |
|---|---|---|
| 到课 | 1 | 固定扣减；若剩余课时不足 1，允许扣至 0 并标记欠费（见 §4.3） |
| 迟到 | 1 | 可按机构配置调整，如按迟到时长折算部分课时 |
| 请假 | 0 | 可配置为扣/不扣；请假不扣课时不影响当次课教师薪资照常核算（因为薪资以课次是否完成为准，而非到课率），机构如需限制请假滥用，可在业务规则层面另行增加请假次数/提前通知时限的约束，本设计不做强制 |
| 缺勤 | 1 | 可配置为扣/不扣 |

### 5.3 薪资计算公式

```
基础课时工资 = 主讲课时 × 课时单价
代课工资 = 代课课时 × 课时单价 × 代课系数
应发工资 = 基础课时工资 + 代课工资 + 奖金补贴 - 扣款
```

- **代课定义**：某课次的主讲教师（class_group.teacher_id）请假或缺席时，由另一教师临时顶替授课，该课次记入顶替教师的"代课课时"而非"主讲课时"。
- **代课系数**：`salary_rule.substitute_rate` 默认建议取值范围 (0, 1]，即代课工资按主讲课时单价打折结算（机构标准做法），若机构需要以加成方式鼓励救场，可配置大于 1 的系数，取值由机构自行维护，系统不做强制约束。

### 5.4 退费金额计算公式

```
可退课时 = lesson_account.remaining_lessons（该课程剩余未消耗课时）
课时单价 = course.price / course.total_lessons
建议退费金额 = 可退课时 × 课时单价 - 违约金（可配置，默认0）
退费金额上限 = 该 enrollment 关联的 payment_record.amount 累计 - 该 enrollment 累计已退费金额
最终退费金额 = min(建议退费金额, 退费金额上限)，若建议退费金额超过上限，系统提示财务人工核实（可能是课程降价或优惠缴费导致）
```

## 7. 异常处理设计

- 全局异常处理器统一返回 `{ code, message, data }`；
- 常见业务异常包括：账号禁用、无权限、排课冲突、教室不可用、课时不足、重复考勤、报名审核状态非法、退费金额超过已缴费上限、薪资单已确认不可覆盖、班级/教室容量已满、报名留位超时；
- Redis 或文件上传异常应提供降级提示，不影响核心数据一致性；
- 所有敏感异常不直接暴露堆栈信息。

## 8. 安全设计

| 安全项 | 设计方案 |
|---|---|
| 密码存储 | BCrypt 或同等强度哈希存储 |
| 鉴权 | JWT + 后端拦截器校验 |
| 权限 | 角色菜单权限 + 接口权限 + 资源归属校验 |
| 数据行级隔离 | 家长端所有按 `studentId` 查询的接口（课表/考勤/学情/课时账户等），Service 层必须校验该 studentId 是否在当前登录家长的 `parent_student` 绑定列表中，未绑定则按 403 处理，防止篡改路径参数越权访问其他家长的学员数据 |
| SQL 注入 | 使用参数化查询，禁止拼接 SQL |
| XSS | 富文本和通知内容做输入过滤与输出编码 |
| 敏感操作审计 | 收费、退费、薪资、权限、公告等写入 operation_log |
| 数据备份 | 提供数据库脚本和初始化数据，正式部署建议定期备份 |
