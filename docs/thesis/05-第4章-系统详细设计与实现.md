## 4.1 招生报名与退费管理

### 4.1.1 报名决策快照与在线报名

家长端报名页面早期版本存在"逐课程串行加载班级并检查报名状态"导致的请求扇出问题：页面需遍历多个课程、逐个请求班级信息与报名状态，不仅响应慢，且用户基于不同时间点的数据做决策容易产生误判。系统在迭代优化中将报名页重构为"一次决策快照"模式。

后端新增报名决策快照服务：一次请求内聚合返回课程列表、可选班级、实时名额、当前报名状态、学员时间冲突与占位到期时间，并为快照生成版本令牌（versionToken）。快照以 5 分钟 TTL 缓存在内存中，前端提交报名时通过 If-Match 请求头携带快照版本，后端校验版本仍有效且决策数据未变化后才创建报名记录。核心实现如下：

```java
// 聚合读模型：一次返回课程+班级+名额+冲突的决策快照
public ParentEnrollmentSnapshotVO getParentEnrollmentSnapshot(Long parentUserId, Long studentId) {
    LocalDateTime snapshotAt = LocalDateTime.now(parentSnapshotClock);
    LocalDateTime snapshotExpiresAt = snapshotAt.plus(PARENT_SNAPSHOT_TTL);
    List<CourseDecision> decisions = buildParentEnrollmentDecisions(studentId);
    String versionToken = snapshotFingerprint(decisions);   // 对决策数据生成指纹
    parentSnapshotRecords.put(versionToken, new ParentSnapshotRecord(decisions, snapshotExpiresAt));
    return new ParentEnrollmentSnapshotVO(snapshotAt, snapshotExpiresAt, versionToken, decisions);
}
```

### 4.2.2 拖拽快速调课与并发控制

为实现"教务在大课表上直接拖拽课次、秒级完成日常调课"的体验，系统在周视图大课表提供编辑模式，使用原生 HTML5 拖放 API 实现课次拖拽（不引入第三方拖拽库）。拖动悬停目标时段时前端基于当前课次做本地预检（教师/教室/班级），将冲突格标红并就地提示；保存时后端以冲突检测结果为最终裁决。快速调课不改变课次的授课教师与教室归属，仅更新上课日期与起止时间，且只允许对"待上课且未开始"的课次操作。

由于快速调课保持课次状态不变（不翻转状态字段），仅靠"状态等于待上课"的乐观条件无法拦截两名教务对同一课次的并发拖拽。为此后端在乐观更新条件中追加"原日期、原起止时间"三个条件：并发第二笔更新时旧时间已不匹配，更新行数为 0，接口返回冲突提示，从而防止一方改动被静默覆盖。核心实现如下：

```java
// CAS：id + 状态 + 旧时间三条件 → 并发第二笔 updated=0 → 409
int updated = scheduleLessonMapper.update(null, new LambdaUpdateWrapper<ScheduleLesson>()
        .eq(ScheduleLesson::getId, id)
        .eq(ScheduleLesson::getStatus, 1)
        .eq(ScheduleLesson::getLessonDate, lesson.getLessonDate())
        .eq(ScheduleLesson::getStartTime, lesson.getStartTime())
        .eq(ScheduleLesson::getEndTime, lesson.getEndTime())
        .set(ScheduleLesson::getLessonDate, request.getLessonDate())
        .set(ScheduleLesson::getStartTime, request.getStartTime())
        .set(ScheduleLesson::getEndTime, request.getEndTime()));
if (updated == 0) {
    throw new BusinessException(409, "课次已被其他教务调整，请刷新后重试");
}
```

调课成功后，系统在事务提交后向该课次关联班级的家长与该课次教师发送调课通知，并记录操作日志。快速调课与教师发起的调课申请审批流（原课次标记已调课、生成新课次并关联来源）双轨并存：前者面向教务日常高频微调，后者面向教师个人冲突与留痕场景。

### 4.6.2 学员流失预警引擎

系统在月度流失率统计的基础上实现学员级流失预警：流失预警引擎以五类因子对在班学员进行打分，分别为到课沉寂度（距最近到课天数）、近期缺勤倾向（近 28 天缺勤占比）、课时余量不足、到期紧迫度与异常出勤加分，总分封顶 100，按分数划分为高风险（≥60）、中风险（30-59）与低风险（1-29）三档。

预警引擎采用可解释的多因子规则（非黑盒模型），每个学员的风险分均可还原为各因子得分与命中原因，便于教务人员理解并采取针对性行动。系统设置防误报规则：班级近期无排课的学员不因沉寂计分；已批准请假不计入缺勤；已退班学员不进名单。预警名单支持按班级/课程/风险档筛选、一键站内触达风险学员家长与 Excel 导出，并记录跟进状态形成闭环。

核心打分逻辑如下：

```java
// F1 到课沉寂度：按距最近到课天数分档计分
private int scoreF1(RiskStudentFacts facts) {
    long days = Math.max(0, DAYS.between(facts.lastAttendanceDate(), LocalDate.now()));
    if (days > 45) return 70; else if (days > 30) return 50;
    else if (days > 21) return 35; else if (days > 14) return 20;
    else if (days > 7) return 10; else return 0;
}
```

## 4.7 移动端功能完善

管理后台功能成型后，系统在迭代优化中着重补齐移动端的能力与信息丰富度，使学员家长与授课教师能将移动端作为日常主入口。本节的四项完善均以"补齐移动端旅程断点、提升家长端与教师端信息对等度"为出发点。

### 4.7.1 教师端学员请假审批

家长端此前已支持提交学员请假申请，但请假申请只能由教务管理员在管理后台处理，授课教师在移动端没有审批入口，形成"家长能提交、教师不能处理"的旅程断点；而后端其实已经具备面向教师的请假查询与审批接口，只是移动端未加消费，属于"接口已备、入口缺失"的功能空洞。为打通"家长提交请假 → 教师审批 → 家长可见结果"的完整旅程，系统在移动端为授课教师补齐了请假审批能力。

教师端新增"学员请假审批"页：进入页面后拉取本班学员的请假列表，列表项展示学员姓名、请假日期、请假原因与状态标签；对处于"待审核"状态的申请，教师可执行"通过"或"驳回"操作，驳回时填写备注（不超过 200 字）。审批的安全性由后端保证：查询接口仅返回该教师授课班级内、在班学员的请假记录，审批接口在更新前二次校验"该教师确在学员请假日期有授课课次"，越权审批会被拒绝；审批本身采用乐观条件更新（仅待审核记录可被更新），并发重复审批时更新行数为 0 并返回冲突提示，避免同一申请被重复处理。审批通过后，家长端该条请假记录即显示"已通过"及备注。审批服务核心实现如下：

```java
// 教师审批：归属校验 + CAS(status=待审核) 防止重复处理
int updated = leaveRequestMapper.update(null, new LambdaUpdateWrapper<LeaveRequest>()
        .eq(LeaveRequest::getId, id)
        .eq(LeaveRequest::getStatus, 1)            // 仅待审核可被处理
        .set(LeaveRequest::getStatus, status)      // 2 通过 / 3 驳回
        .set(LeaveRequest::getAuditUserId, teacherId)
        .set(LeaveRequest::getAuditRemark, remark));
if (updated == 0) {
    throw new BusinessException(409, "该请假申请已被处理，请刷新后重试");
}
```

### 4.7.2 课表 Tab 真实化与教师课表富信息

移动端底部"课表"主 Tab 此前仅负责跳转、内容恒为"今天没有课程安排"，是一个高频入口的空壳页，与家长端、教师端已有的课表能力不对等；同时教师端课表页只显示"班级 ID / 教室 ID"这类裸编号，不显示课程名、班级名与状态，信息丰富度明显低于家长端课表。

系统在迭代优化中将课表 Tab 重构为按角色自适应的真实课表页：家长进入时加载当前学员的课表，教师进入时加载其授课课次，页面统一过滤出"今日及未来 7 天"的课次并按日期分组、今日课次高亮；有课时展示课程名、班级名、时间与状态，无课时展示真实空态并保留"查看完整课表"入口，不再出现恒显示无课的伪内容。教师端课表页同步补齐信息，展示课程名、班级名、教室名、上课时间与状态，移除裸编号展示，点击待上课课次可直接进入课堂考勤。为支撑教师课表的教室名展示，后端课次查询服务补充了教室名称回填（复用已有的教室数据访问），一处改动同时服务课表 Tab 与教师课表页。日期过滤与分组逻辑被抽离为可复用的纯函数，便于后续维护与测试。核心实现如下：

```javascript
// 课表日期分组（纯函数）：按 lessonDate 升序返回 [{ date, lessons }]
export function groupLessonsByDate(lessons) {
  const map = new Map()
  for (const l of lessons) {
    const d = String(l && l.lessonDate).substring(0, 10)
    if (!map.has(d)) map.set(d, { date: d, lessons: [] })
    map.get(d).lessons.push(l)
  }
  return Array.from(map.values()).sort((a, b) => (a.date < b.date ? -1 : a.date > b.date ? 1 : 0))
}
```

### 4.7.3 消息未读角标

移动端的调课通知、上课提醒、课时不足与机构公告等消息此前只能在进入消息中心后逐条查看，入口本身没有任何未读提示，用户容易错过关键提醒。

系统为消息入口增加未读角标：移动端在首页与消息页显示时拉取当前用户的未读消息数，数量大于 0 时在"消息"Tab 上以数字红点展示（超过 99 显示"99+"），无未读时移除角标；用户打开消息中心或点开单条消息后重新拉取未读数，角标随之更新。未读数查询为全角色通用端点，家长、教师与教务共用同一实现。角标文案由独立纯函数负责，便于统一口径与测试，核心逻辑如下：

```javascript
// 未读角标文案与显示判定（纯函数）
export function formatBadge(n) {

export function shouldShowBadge(n) {
```

### 4.7.4 家长端学情上下文补全

家长端学情页此前在考勤记录中只显示"课次 ID"，家长看到的是没有业务含义的编号，无法判断孩子是在"哪一天、哪门课、哪个班"的表现如何。

系统将家长端学情页的考勤行由展示课次编号改为展示后端已返回的课次上下文信息（格式为"班级 日期 时间"），家长可直观看到每一条考勤对应的具体课次；作业与评语在接口返回课程、日期信息时一并展示。该改动为纯前端展示层调整，业务数据口径与后端保持一致，不改变任何业务规则。

### 4.7.5 移动端纯逻辑单元测试

为延续系统的测试纪律，本次移动端补充/改动涉及的纯逻辑均被抽离为独立模块并配以单元测试，包括报名决策快照、课表摘要（日期过滤与分组）、请假状态文案与审批可操作性判定、未读角标文案与显示判定等，共同构成 4 个测试文件、25 个用例的移动端测试集，确保移动端的核心展示逻辑可回归、可验证。

## 4.8 本章小结

本章围绕招生报名、排课调课、考勤课时、财务薪资、学情考级、运营看板与流失预警以及移动端功能七个方面，阐述了系统的核心模块设计思路与关键实现。在报名退费环节，以"报名决策快照 + If-Match 版本校验"保证决策数据一致性，以乐观并发控制与数据库唯一约束保证退费审核的并发安全；在排课调课环节，以五维时间交叉冲突检测（教师、教室、教室预约、班级、跨班学员）与拖拽快速调课提升易用性，并以"状态 + 旧时间"复合乐观条件防止同状态并发编辑相互覆盖；在考勤课时环节，以严格状态校验与请假保护保证"请假不扣课时"规则不被绕过，并实现课时扣减的并发安全与幂等；在财务薪资环节，以状态机与并发控制相结合的核算体系实现薪资自动核算；在运营看板环节，以多因子可解释规则构建学员流失预警，将运营统计升级为流失干预决策；在移动端环节，重点补齐教师请假审批、真实化课表、消息角标与家长学情上下文，使移动端成为家长与教师的日常主入口。上述实现共同支撑了第 3 章设计的落地，形成覆盖全流程、可测试、可上线的教务管理能力。
