## 一、背景与根因

导师反馈「对教师的管理功能比较匮乏」。经 22 轮多视角评审（产品 / 安全 / 实现）确认：

**根因不是功能少，而是入口挂错了角色。**

| 事实 | 位置 |
|---|---|
| 用户管理控制器整类只放行超管 | `modules/user/controller/UserController.java:22` `@RequireRole({"SUPER_ADMIN"})` |
| 教务角色的菜单白名单里没有教师管理 | `sql/data.sql:51-63`（`EDU_ADMIN` 授权列表） |

后果：建教师、改、禁用、重置密码、维护可授课程——**只有 1 个超管能操作**。教务天天管人，却在系统里碰不到教师。那 1 个超管不在时，教师入职和交接就停在口头。

因此本次改造的**第一优先级不是加功能，是挪权限**。

### 三态定义（读时计算，不落库）

| 条件 | 展示 | 标签色 |
|---|---|---|
| `status != 1` | 已离职 | info |
| `status == 1` 且 `leave_date` 为空 | 在职 | success |
| `status == 1` 且 `leave_date` 在未来 | 将于 YYYY-MM-DD 离职 | warning |
| `status == 1` 且 `leave_date` 已到/已过 | 已过离职日未停用 | danger |

> 判定必须用 `!Integer.valueOf(1).equals(status)`，**禁止写 SQL 的 `status <> 1`**——`status` 为 NULL 时 `NULL <> 1` 返回 NULL 而非 TRUE，会漏掉最该拒的脏数据。`JwtInterceptor:79` 的注释记录过线上出现过 null。

### 三个关键实现约束

**① 换任课教师绝不改已完成课次**

```java
// CourseServiceImpl.transferTeacher
scheduleLessonMapper.update(patch, new LambdaQueryWrapper<ScheduleLesson>()
        .in(ScheduleLesson::getId, lessonIds)
        .eq(ScheduleLesson::getStatus, 1));   // status 恒为 1，永不出现 2
```

原因：薪资按 `teacher_id + status=2` 聚合，改了会静默重写历史账目。

**② 强制改密的两处 return 位置**

| 场景 | 要求 | 违反后果 |
|---|---|---|
| 未命中白名单 | 必须在 `CurrentUserHolder.set()` **之前** return | ThreadLocal 泄漏到线程池工作线程 |
| 命中白名单 | **不能** early return，必须继续走到 `set()` | `/api/auth/password` 里 `get()` 直接 NPE，且只在这一条路径复现 |

白名单仅 4 条：`/api/auth/password`、`/logout`、`/profile`、`/menus`。

**③ 改密后签 token 必须同事务重查**

```java
userMapper.update(...);                    // setSql("version = version + 1")
User refreshed = userMapper.selectById(userId);   // ← 重查，不能用「旧值 + 1」猜
String token = jwtUtil.generateToken(refreshed.getId(), refreshed.getUsername(),
        refreshed.getRoleCode(), refreshed.getVersion());
```

并发下（如同时被禁用或改角色）若用猜测值，签出的 token 会立刻失效。

## 八、明确不做的项（附理由）

| 不做的项 | 理由 |
|---|---|
| 教师自助注册 | 会开一个越权入口；正确做法是管理员建号 |
| 激活码 / 邀请码 | 项目没有真实短信通道（`MockSmsNotificationChannel` 仅打日志），码只能管理员转发，管理员必然持有可接管凭证，卖点不成立；成本却要表 + 接口 + 限流 + 状态 + 重发 |
| 批量导出家长联系方式 | 脱敏后无增量价值；且它正是「学员被带走」这个风险的工具化 |
| 教师考核评价（评分 / 听课） | 15 个教师样本极少，评分权重无依据，一挂薪资就回到金额正确性问题 |
| 教师档案字段堆砌（工号/学历/教龄/证书） | 一次性录入、一年看两次，不产生业务流转；**详情页本身就是档案** |
| 教师请假 | 低频，且会牵出代课指派与课时归属的大改造 |
| 教师可用时间 / 最大周课时 | 依赖排课并发 P0（排课本身无 DB 排他约束），做它要先修 P0，工时翻倍 |
| 手机号唯一约束 | `user` 用软删除，唯一索引连已删行一起算（`username UNIQUE` 已踩过这坑） |
| 每日配额 403 | 上限恰好等于可达最大值，**永不可达**——死分支，评审必被问 |
| 24 小时自动解锁 | 15 人机构里等于「用户静默流失」，没人能帮他解开 |
| 学员列表手机号脱敏 | 需要先有学员详情页（`GET /students/{id}` 前端零调用），属另一主题 |

## 十、答辩可用表述

**关于根因**

> 教师管理功能的匮乏，根因不是功能少，是入口挂错了角色。改造前 `UserController` 整类只允许超管，教务的菜单白名单里也没有教师管理——教务天天管人，却在系统里碰不到教师。所以这次第一件事不是加功能，是把权限挪到真正用它的人手上。

**关于联系方式**

> 本系统不阻止教务访问全量学员信息，这是业务需求；控制手段是审计而非阻断。教师侧不提供批量出口，仅按任教关系单条查看并全程留痕。若需更强隔离，应引入按班级/角色的数据范围模型，而不是在导出按钮上做限制。

**关于密码与审计**

> 管理员知道密码不可怕，可怕的是他不知道「自己知道」这件事会被看见。

### 11.2 顺带修复的既有 bug
